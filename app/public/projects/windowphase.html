Personal project · Engineering case study

windowphase

A workday schedule you can inspect before running.

I wanted to see whether a fixed usage-window schedule could line up with my working hours. windowphase makes the timing, baseline, and clock-in command explicit before a live request.

  • Python
  • Scheduling
  • CLI

The workday problem

If a provider uses a request-anchored window, the time of the first request shapes when the next reset arrives. Those boundaries can fall outside the hours when the allowance is useful.

windowphase models a five-hour window against the workday and looks for reset boundaries that leave usable portions of time on either side. It compares the proposed schedule with the no-tool baseline, so the calculation has a concrete point of comparison.

The choice I made

I separated the planner from provider execution. The Python calculation returns pre-work ignition, reset times, and reachable windows under a minimum usable-slice constraint; spacing validation also checks the gap across midnight.

Provider adapters build explicit command arguments, and the runner defaults to a dry run. A live clock-in requires live=True or --live. This makes the plan inspectable, while leaving the real provider behavior and request cost as assumptions that must be checked separately.

Illustrative model example — not an account measurement

For a 09:00–18:00 workday and a 60-minute minimum usable slice, the anchored model places clock-ins at 06:00, 11:00, and 16:00. These are calculated times under the model, not a measured account benefit.

What it produces today

The project provides schedule calculation and rendering, a no-tool comparison, provider command previews, a ledger, and health-check code. Scheduler representations exist for systemd, launchd, and Windows Task Scheduler.

The bounded result is a calculated schedule and an inspectable CLI path. A rolling lookback may make the anchored model unsuitable; actual quota benefit and parity across Linux, macOS, and Windows remain unestablished.
